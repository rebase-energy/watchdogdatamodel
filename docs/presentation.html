rebase-energy / watchdogdatamodel

The watchdog, distilled to its data model.

A reusable blueprint for timeseries data quality — extracted from the grid-map watchdog, designed for every Rebase product that watches data: detect → track → act → verify against the data itself.

the signature problem: a gap in a series — and everything that should happen next

built on timedatamodel — so it works for forecast data quality too (valid time + knowledge time, native)

why touch something that works

The watchdog is fine.
Its database grew wild.

01

Nine tables, grown one feature at a time, tied to grid-map vocabulary (zones, sweeps, backfills).

02

Three issue-identity schemes — issue_id · issue_key · cluster_key — that never match each other.

03

The board's issue id hashes the flagged timestamps — so the same problem changes identity as a gap grows, orphaning its history.

04

Most joins happen by matching zone strings, not keys. And every other product would need this machinery rebuilt.

the redesign

Seven tables, one spine.

Every table reaches issue or series in one hop, by real foreign keys. The core never says “zone”, “backfill” or “sweep” — machinery in the core, vocabulary in the product (labels, check ids, action types, board stages).

the rules that do the heavy lifting

Small model, strict physics.

Each rule is enforced by the database itself — constraints and triggers, not good intentions.

Coverage, not silence

Runs declare their scope before running; nothing stores “everything’s fine”. Healthy = covered by a completed run + no open issue. A source we couldn’t even fetch becomes an issue, never a blank.

Dedup by constraint

One fingerprint (series + check) → at most one open issue, enforced by a unique index. The same gap seen five nights in a row is one issue touched five times — duplicates are impossible, not discouraged.

Incidents, with memory

A problem that returns after being resolved opens a new issue linked to its predecessor. January’s outage and June’s parser bug stay separate stories — incident counts and time-to-resolution stay honest.

Data truth > process truth

A successful backfill or a merged PR never resolves an issue. Only a later run that covers the series and finds nothing does. Code that doesn’t fix the data doesn’t get to claim victory.
